## Session Notes

### Pre-session code review findings (file:line references)

1. **As-built diverges from architect's plan (informational, not a defect)** — `comments.md` Architect Annotation describes a `pg_cron`-driven Supabase Edge Function `process-import-jobs` reading creds from `workspace_integrations` (Vault-encrypted). The shipped implementation instead runs the worker inline via Vercel `after()` (`app/api/v1/imports/route.ts:6,87`) with a single-tenant, server-role admin client (`lib/jira/import-runner.ts:8,40`) and env-var creds `ATLASSIAN_URL` / `ATLASSIAN_EMAIL` / `ATLASSIAN_API_TOKEN` (`lib/env.ts:36-38`, `lib/jira/client.ts:116-122`). Ely's "Ready For QA" comment confirms this is the intentional MVP shape — `workspace_integrations` table does not exist. Treat as as-built ground truth, not a gap.
2. **"One active import per project" 409 — DB-level race-proof, not app-level-only** — migration `0020_import_jobs_one_active.sql` replaced a plain index with a **partial UNIQUE index** `import_jobs_one_active_per_project on (project_id) where status in ('queued','running')`. The route does a fast-path SELECT check first (`route.ts:49-63`, returns 409 `import_in_progress`) AND catches the `23505` unique-violation from the INSERT as a fallback (`route.ts:77-82`) — so the race window the shift-left review worried about (Gap #5, "Concurrent imports... race") is closed at the DB layer. Good: this directly answers Critical Question #2 from the shift-left refinement (serialize via 409 — chosen).
3. **Crash recovery = re-run, not resume (Option A from shift-left CQ#1)** — `import-runner.ts:43-58` atomically claims a `queued` job via `UPDATE ... WHERE status='queued'` (compare-and-swap, no `FOR UPDATE SKIP LOCKED` despite the architect's note — simpler CAS achieves the same single-claim guarantee). Any throw after the claim lands the job in `failed` (`:122-129`), never stuck in `running`. There is **no checkpoint/resume**: `next_page_token` is persisted per page (`:97-107`) but is NOT read back on a fresh run — `executeImport` always starts `pageToken = null` (`:71`). Ely's note confirms "a re-run is always safe (idempotent), which is also the crash-recovery path" — i.e., Option A was chosen, the `next_page_token` column is currently write-only telemetry (visible on the job row while `running`, ignored on restart). This resolves shift-left Gap #1, but **a worker crash mid-job leaves the job stuck in `running` forever** (no timeout sweeper exists — Top Suggested Improvement #1 from shift-left was NOT implemented). Worth probing in Stage 2 if we can simulate it; otherwise note as a residual risk.
4. **Credential failure → `jira_unauthorized`, whole job fails (resolves shift-left Gap #2)** — `client.ts:120-122` throws `JiraAuthError` when any of the three env vars is missing, and `:143-145` throws the same on HTTP 401/403. `import-runner.ts:122-124` maps `JiraAuthError` → `errors[].code = 'jira_unauthorized'`, `status = 'failed'`. This is exactly Ely's AC6 / the shift-left's suggested improvement #2 (though the code is `jira_unauthorized`, not the suggested `JIRA_AUTH_FAILED` — naming differs, behavior matches).
5. **ADF node support list (resolves shift-left Gap #3)** — `adf-to-markdown.ts:29-51` supports: `doc`, `paragraph`, `heading` (h1-h6 clamped), `bulletList`/`orderedList`/`listItem`, `codeBlock` (with language attr), `blockquote`, `rule` (`---`), plus inline `text`/`hardBreak`/marks (`strong`, `em`, `strike`, `code`, `link`). **Unknown/unsupported nodes** (tables, panels, expand/emoji macros, media, mentions, status lozenges) fall through to `renderUnknownBlock`/`renderInlineNode` (`:105-110`, `:127-132`) — they recurse into `content` if present (flattening structure, e.g., a table becomes its cell text run together) or degrade to `node.text ?? ''`. **Nothing throws** — degrade-gracefully, no `errors[]` entry for unsupported nodes. This is graceful-degradation, not the "document what strips/converts/errors" the shift-left asked for; worth a light spot-check with a table or panel in Stage 2 if a suitable Jira issue exists.
6. **AC heuristic (resolves shift-left Gap "AC extraction algorithm" ambiguity #4)** — `extract-acceptance-criteria.ts:9-18,30-68`: anchors on a line whose stripped text matches `/^(?:acceptance criteria|acceptance criterion|ac|criteria)\s*:?$/i` (heading markers and `*` emphasis stripped first), then collects consecutive bullet/numbered list items until a heading (`#`) or a non-list non-blank line. Horizontal rules / blockquote lines are *skipped* (not stop conditions) because ADF emits `---`/`> ` inside legitimate AC blocks. Truncates each title to 200 chars. **Note**: per Ely, "Acceptance Criteria are extracted from the description body only — issues that keep ACs in a Jira custom field import 0 ACs (expected)". This also resolves shift-left Gap #4 ("Jira custom fields silently discarded") for the AC-specific case — confirmed expected, not a bug.
7. **Idempotency key + reconciliation (resolves shift-left ambiguity #3 + Gap #4 generally)** — `external_id = issue.key.trim().toUpperCase()` (`import-runner.ts:210`), upsert-by-lookup on `(project_id, external_id, archived_at IS NULL)` (`:217-223`). Re-import of an existing story updates ONLY `title`/`description` — module placement and status are left untouched (a possible manual move survives re-import) (`:228-235`). AC reconciliation (`:257-283`) appends only criteria whose `lower(title)` isn't already present (no dedup-by-position, additive-only — manually edited/removed ACs are not restored or removed by re-import). Other Jira fields (epic link, story points, labels, fixVersions, priority — shift-left Gap #4) are read in `SEARCH_FIELDS` only as `summary, description, components, issuetype` (`client.ts:76`) — everything else is genuinely discarded, confirmed out-of-scope per Ely's Phase-2 list ("custom-field mapping").
8. **429 backoff** — `client.ts:79,87-96,147-153`: schedule `[1000, 2000, 4000, 8000, 16000]` ms, honors a numeric `Retry-After` header over the schedule, throws plain `JiraError(429)` after exhausting 5 retries (this becomes a per-page fatal → job `failed` with code `job_failed`, NOT `jira_unauthorized`). Matches the architect's spec (max 5 retries) but note: a 429-exhaustion failure surfaces as generic `job_failed`, not a distinguishable rate-limit code — minor observability gap, not an AC violation.
9. **Chunking / pagination** — `PAGE_SIZE = 100` (`:27`, matches Jira Cloud's hard ceiling per the architect's note), `MAX_PAGES = 1000` backstop against a non-terminating cursor (`:29,111`). Each page's counts are persisted immediately (`:97-107`) so polling reflects partial progress; loop exits on `isLast`, `null` cursor, a **stuck cursor** (`next === pageToken`), or the page ceiling (`:111`). AC5 "Chunking" (≤100/page, final `imported_count` = total) is directly testable if we can find/construct a JQL returning >100 issues — may be hard on the real `upexgalaxy` Jira; flag as a Stage 2 feasibility check.
10. **Truncation at 50 KB (resolves shift-left CQ#3 — "truncate with marker")** — `import-runner.ts:25-26,285-295`: `MAX_DESCRIPTION_BYTES = 50 * 1024`, byte-aware truncation loop appends a visible Markdown blockquote marker. Confirms "truncate with marker" was the chosen option.
11. **Inbox placement (resolves shift-left ambiguity #2)** — `ensureInbox` (`:168-200`) creates Inbox as a **root-level module** (`parent_module_id: null`), positioned after existing root siblings via `nextPosition`. DB ground truth confirms this already happened once: project "Smoke Checkout" now has an `Inbox` module at root (`position: 2`, alongside `Payments` and `Refunds and Credits`) — almost certainly created by the BK-9-session import test run referenced in the orchestrator's pre-gathered facts.
